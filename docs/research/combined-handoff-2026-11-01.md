## 一、先说结论

AG Relay 已经不是简单的“失败就重试”脚本，而是一个同时管理**请求重试、历史兼容、流式交付、取消与排空、桌面诊断和安全更新**的完整产品。

两边材料合起来，最重要的认识是：

1. **目标是让原任务继续，而不是把错误藏起来。** 不该为了减少红字，让同一请求无进展地重复几百次；也不该为了快一点结束，掐掉本来能成功的慢请求。
2. **几种恢复不能混为一谈。** 普通重试、首发去编号、有损历史降级、绑定失效去编号、缓存键恢复，触发条件、删除范围、次数和记忆方式都不同。
3. **v0.3.18 已经实现并发布有限缓存键恢复。** “持续限流时永远只会原样重试”是旧版缺口，不能再拿它描述最新代码；但原公司 Codex 故障的严格对照和升级后的持续使用效果仍有证据缺口。
4. **目前最值得整理的是职责、状态和说明的一致性，不是全量重写。** 先弄清一次请求经过哪些步骤、何时修改了什么、为什么继续或停止，再决定是否局部拆分模块。
5. **稳定性与上下文优先。** 正常可用流程、客户端原生身份、工具配对和已经交付后的不重放保护，不能为新补丁让路。

## 三、用户诉求与不能丢的取舍

- 尽可能在原对话里继续工作，不默认要求空白重开，也不默认删除旧推理。
- 偶发故障能内部恢复；恢复不了时不能长时间装作“仍在修复”。
- 正常请求仍及时交付，不为了拦截所有后续错误而缓冲整段回答。
- 已交付的正文、推理、搜索完成结果或客户端工具不重放，避免重复输出、重复改文件或执行命令。
- 客户端 UA、originator、会话/线程标识等原生身份不能伪造或随意移除。测试也遵守，不拿改身份后得到的 401 解释原故障。
- 日志要能解释等待与失败，不记录聊天正文、密钥和任意身份字段。诊断数据缺失时承认缺口，不把没有日志解释成没有问题。
- 改动要让用户能感到更稳、更少等待、更容易定位；不是以删了几行代码、跑了多少测试作为主要成果。
- 开发、构建、发布由 AI 在授权范围内完成；用户多次选择自行应用内更新，发布不能顺带安装、退出或重启现用网关。
- 不把历史的测试、部署、权限授权带到这轮。公司文件中的启动建议也是背景材料，本轮用户只要求总结。

### 4.2 一次请求的行为路线

下面是阅读代码的行为地图，不是要求按此拆成文件的架构方案：

> 接收请求与安装取消监听 → 判断实际协议/客户端 → 编译本次策略 → 计算各类会话/缓存作用域 → 执行允许的首发处理 → 在次数与时间预算内请求上游 → 判断错误或流式事件 → 选择对应恢复或交付 → 完成、明确失败、取消或预算结束。

几个最重要的分岔：

- **普通 HTTP 错误、HTTP 200 中的 JSON 错误、尚未交付的 SSE 错误**：都需要按明确错误证据判断，不能只看 HTTP 状态码。
- **尚未交付的可恢复错误**：可以在规则允许时改写/重试；状态修复、历史修复、绑定修复和缓存键恢复各有条件。
- **空占位、特定未完成搜索**：继续缓冲，不等于已经交付真实内容。
- **真正交付以后**：不再重放整条请求；后续失败可能仍需要客户端处理。
- **取消**：打断等待、退避与正在读的上游请求；不能等睡眠结束后再偷偷发一次。
- **正常长流**：不能因为重试总预算到点而被截断。
- **多层重试**：客户端、CC Switch/CCS、VPS/本地核心、模型服务可能各自重试；单层有上限，不等于用户整次任务总等待有上限。

## 五、恢复机制速查：同一个“修复”字眼下面其实有不同动作

| 机制 | 触发/作用域 | 改什么、不改什么 | 记忆与限制 |
| --- | --- | --- | --- |
| 常规重试 | 明确临时故障；取决于错误类别及当前阶段 | 通常重发当时的请求，不因此删历史 | 次数、退避、剩余时间和取消控制；不能承诺每次都换到其他通道 |
| Codex 可选首发去编号 | 当前首发策略允许 | 去允许清理的顶层 item id，推理内容不等于被删 | 遇到搜索依赖要保守；`removedReasoning=0` 不能解释成有损降级 |
| 明确历史错误后的兼容恢复 | 配置、确认次数、错误种类、完整历史检查都满足 | 某些路径会成组删除旧推理及依赖编号，保留正文和完整工具配对 | Codex 真正有损恢复有专属发送限制；既有历史兼容记忆不等于成功后才登记 |
| 会话兼容预清理 | 之前已登记对应兼容模式 | 可能对整组历史处理，不是只处理最后一条 | 不能因为用了预清理，就把纯限流也限制成三次 |
| v0.3.17 绑定失效恢复 | 严格 Codex Responses，具名错误/明确文案；裸数字 `30013` 不够 | 当次只去顶层编号，推理密文/摘要、工具/搜索载荷、客户端身份保留 | 至多一次；拒绝不完整或服务端引用历史；不写有损兼容缓存，失败不继续删推理 |
| v0.3.18 缓存路由恢复 | 无冲突识别的 Claude/Codex Responses，自带非空 `prompt_cache_key`，连续两次明确限流 | 只替换缓存键；该动作不改历史、原生身份头或会话元数据 | 剩余预算内至多一次；成功才记忆，按上游/凭据/模型/原键隔离；新键可能有冷缓存成本 |
| 空回应分级处理 | 某些既有通用路径、配置门槛及实际形状条件 | 与明确限流、Codex 历史恢复不同 | 不能把“连续六次 limit 就删推理”当成现行统一规则 |

**关键区别：**缓存亲和键不是会话身份，但也不能随便改。家里 10 月 31 日要求 `prompt_cache_key` 不变，是为了当时“只去编号”实验的一变量对照。公司随后专门批准并验证的 v0.3.18，新增了一个有条件的改键动作。两者并不授权网关在所有请求中改键，更不授权改 UA。

**动作无损不等于整条路径无损：**v0.3.18 新增换键本身不删推理，但已登记兼容预清理或明确跨资源历史错误仍可能触发旧有损处理。报告必须逐步列出实际改动，不能只描述最后一个成功动作。

## 六、两边证据对照：哪些结论更新了

| 旧判断/容易误读之处 | 合并后应采用的判断 |
| --- | --- |
| 请求没经过本机 AG Relay，所以不是网关问题 | 家里后来确认远端还有同源核心；必须把完整链路查清，旁路本机不等于旁路所有网关 |
| 搜索附近出错，所以搜索导致上游限流 | 已证实的是未完成搜索过早交付使后续限流穿透；未证明搜索造成上游限额耗尽 |
| 没有可见正文，就可以安全重放 | 加密推理、搜索完成、客户端工具、未知载荷也是安全边界；可见文字不是唯一标准 |
| 分叉更换会话编号，就能解除绑定错误 | 原生分叉确实保留历史且换编号，但用户实际仍失败；不能继续当已验证解决方案 |

| 绑定恢复验证成功，所以全部 `30013` 都解决 | 最终真实对照已变为历史类 400，未稳定复现原 409；证明该旧历史可恢复，不证明所有绑定失效情况 |
| Claude 一定是 Messages、Codex 才是 Responses | 家里某次查到 Claude 配置为 Messages；公司另有 CCS 转 Responses 链路。按网关实际收到的协议判断，不能按客户端名字推断 |
| `rate_limit_exceeded` 说明模型整体不可用 | 家里旧请求失败时，新对话同时首试成功；问题与具体请求条件相关，错误码本身解释不完 |
| 持续限流没有任何处理办法 | 公司受控对照支持缓存亲和性相关的恢复；v0.3.18 已落地有限换键，不要重新立项实现同一能力 |
| 缓存键一定把请求固定到某一耗尽账户/通道 | 没有观察服务内部调度。实验证据支持与缓存键相关，不支持把内部具体分配方式写成事实 |
| 所有已完成测试都对应公司原 Codex 故障 | 原 Codex 两次重建请求停在 401；Claude 重建历史的成功不能替代其严格 A/B |
| 约 17.37 万输入 token 是旧主对话规模 | 公司复核指出那是子任务；主对话最后成功回执约 30.68 万。不能据这两个数推出长度阈值或根因 |
| UI 上显示 Sonnet，后端就是 Sonnet | 家里一次调用主动指定别名，返回模型标识为 DS。别名、实际模型与能力预期需分开；本轮未改选模设置 |

### 6.1 家里绑定恢复的证据

- 真实请求共 18 次；两次改变 UA/身份的对照被上游以 401 拒绝，已排除。
- 早期测到的是后台历史整理，不是普通续聊；后续校正模型定义和请求后才验证真正续聊。
- 原生 Codex、`xhigh`、同身份的有效最终对照：现网形状保留 24 个推理编号和 3 个搜索编号时返回历史错误；只再去掉这些编号后返回正文及完成事件。
- 推理密文、6 段可读摘要、正文、工具参数/结果与搜索内容保留。原任务返回的工具没有执行。
- 最终没有稳定重现原 409，不能用“后续成功”填平这一证据缺口。

来源：[本地研究记录](session-binding-recovery-2026-10-31.md)及[绑定恢复现行边界][binding]。本地研究文件仍保留“尚未实施”的阶段口径，后续产品状态由 v0.3.17 提交与发布记录更新；本轮未修改这个原研究文件。

### 6.2 家里发现的空转与公司后续实验

**家里当时看到：**一条旧请求连续 94 次同码失败，无正文/思考/工具输出；旧历史 257/259 条，含 83 条推理，新对话首轮约 5 条。同一时间新对话连续首试成功。旧请求已首发去编号，不能再靠同样去编号产生新变化。原公司请求不在家里，家里这一轮真实模型调用为 0。

**公司后来补上：**相同重建 Claude Responses 历史变体，旧缓存键约 9.5 秒限流，只换缓存键约 42.7 秒完成。通过修改后的独立核心，两次复验分别约 46.4 秒和 51.6 秒，均四次上游尝试后完成。

解释范围：

- 公司核对了 152 条来源消息摘要，但 Responses 是按转换规则重建，不是原生请求字节级重放。
- 两次独立核心复验均先处理既有跨资源历史错误，然后两次限流，最后换键；其中记录到删除 84 条旧推理。这是该 Claude 实验，不要与家里 83 条推理的 Codex 样本合并。
- 完成依据是 API 完成事件，模型提出的工具未执行；不等于原业务已完整做完。
- Codex 范围有类似旧日志和隔离回归，扩围已发布；原公司 Codex 现场严格 A/B 仍未完成。
- 同类多次限流在更早版本日志已存在，因此不能仅凭时间接近就归因于 v0.3.16/v0.3.17 新引入；早期出现不等于排除了所有可能的后续交互问题。

### 6.3 其他容易误判的运行证据

- 供应商的 `client cancelled` 可能是网关超时后取消某次尝试，不一定是用户点击停止，也不自动等于 Codex 后台审核。
- 0 token/无用量回执不证明没有发送内容或没有费用；错误行数不等于失败任务数。
- 日志曾达到容量后停写；缺日志时不能证明网关一直正常。连续写入及容量问题后来已修，不要再次当全新需求。
- 本地 requestId 不是上游追踪编号；SSE 使用 HTTP 200 也可能带上游响应头。未采集的旧编号无法事后恢复。
- 家里另外的 HK/新加坡 WebSearch 故障只是相邻工具/供应商现象，未证明 AG Relay 核心参与，不能直接并入“网关搜索修复失效”。

### 6.4 VPS 邻接系统：需要记录，但不能混成核心缺陷

本机 Codex 存档补充了另外三类上下文，均为历史报告，本轮未重新验收站点：

- 最初想把完整恢复引擎直接整合进 new-api/sub2api、取消独立网关，后来实际仍是站点转发到独立核心；“已经完全整合”不成立。限定指定 AG 账号/Responses 的要求，也不是把有损策略扩大到所有账号。
- 10 月 31 日曾报告某客户端的 `unauthorized_client_error` 导致站点停用整条 AG 账号，后续 Codex 在进入网关前得到 503；当时提出“不因单个客户端不获准就锁整个账号”的例外，未实施。它属于站点账号调度，不是本轮证实的 AG Relay 重试回归。
- 10 月 22 日记过 new-api 取消后可能继续内部重试；后来的站点升级报告不足以证明该点已闭合。站点短时假上游验收也没有覆盖完整 500 秒耗尽。

这些是跨层排查时应核实的旧线索，不自动新增待办、不直接修改邻接项目。计费倍率、账号状态和站点模型清单不是 AG Relay 的默认策略，本文不复制生产配置。

## 七、按四类保存现状

### A. 已落地

- 关窗的取消/留托盘/彻底退出选择、真实更新阶段；外部网关保留安全停止/重启，但须归属核实、醒目标记与确认，不照抄设计稿的外部实例只读。

- 取消、统一错误分类、完整工具历史、会话兼容记忆、策略配置和 v0.3.13 次数作用域修复。
- v0.3.14 等待取舍，v0.3.15 空占位、v0.3.16 搜索交付、v0.3.17 绑定恢复。
- v0.3.18 有限缓存键恢复：已入库并公开，不是待写的方案。
- VPS v0.3.16/v0.3.17 的受控部署在家里会话里有完成记录；服务器有用户隔离与独立部署错误计数等定制，不是桌面文件的可盲覆副本。

“已落地”不等于这台机器已经安装，也不等于所有真实业务场景已验收。

### B. 曾讨论但未实施，或后来未采用

- “低频错误要不要继续追查”和“失败怎样更诚实地结束”是不同问题。Codex 部署旁支中，用户明确不满意只补一个失败终点，目标仍是尽量在内部恢复；助手当时提过只对 AG Codex 整段缓冲，但没有上线，也不是现行策略。
- 全局激进去掉历史、推理、搜索等字段：没有作为默认方案采用。
- 网关自动更换会话身份：家里早期讨论过，最终 v0.3.17 采用只去条目编号，不是该方案。
- 只要包含搜索就一律拒绝恢复、完全不跨请求记忆：属于早期保护/阶段选择，已被后续有条件方案替代，不能回退照搬。
- 核心全面模块化：尚未完成；策略页配置项分组不等于代码职责已经拆好。
- 通过采集更多数据解释超时/追踪编号：部分曾讨论，不能说已全部落地。

- 10 月 16 日诊断停更调查中提出的整套健康提示与失败退避计划被叫停；后来日志续写修复不等于整个计划都实现。

## 九、验证与操作边界

- 桌面策略两组目前概要：常规尝试 110 次、基础/最大退避 500/1000 毫秒、总预算 500 秒、基础响应头等待 220 秒、历史 `on_error`、确认 1 次、允许会话记忆。**不是独立核心所有环境的统一默认值，也不是特殊恢复的统一上限。**
- 优先临时目录、随机端口、假凭据、假上游；只清理自己创建并持有的测试进程。
- 不运行会触碰现用默认端口、真实 AppData、自启注册表或广播停止信号的无过滤测试；不为测试停止现用网关。
- 按变更范围使用[策略测试][policytests]、[历史测试][historytests]、[排空测试][draintests]及相关 Rust 接缝；纯文档不编译不打包。提交或发布本身不是重跑所有测试的理由。
- 必须区分：检查拒绝、构造了恢复请求、实际发出、上游完成、工具执行、业务完成。HTTP 202 也仅表示受理控制请求，不代表排空/重启完成。
- “缺旧核心基线”与“缺真实上游”不是同一个缺口。v0.3.13 的五项本地差分曾被历史报告误称需要真实通道；现行 README 已更正，不能为这些离线对照无谓发付费请求。
- 真实实验需要有效原生身份、模型与工具配置、正确中间链路；限定总尝试次数和截止，不让“调用一次测试”内部无限重试；返回工具不执行。
- 更新用原生产签名，复用缓存和现有入口；更新签名不是 Windows Authenticode 发布者证书。
- 密钥、完整业务对话、原请求/响应、生产配置不进入总结、GitHub issue 或仓库。VPS 只在独立授权后按实际状态备份/排空/替换网关，不动两站服务、渠道、价格和其他组件。
