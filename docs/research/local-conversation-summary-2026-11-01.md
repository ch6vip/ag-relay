> 整理日期：2026-11-01。用途：提炼家里这台电脑上的项目决策、实际故障、用户纠正和验证边界，不复制原始对话。

## 1. 阅读范围

- 桌面应用中 **18 个直接相关对话记录均已完整分页读到开头**：17 个在 AG Relay 项目目录，1 个是另目录的 README 讨论。共 12,636 条接口返回记录，包含工具折叠项、注入说明、父子分叉和重复前文，不等于同数量的用户消息或 18 场独立研究。
- 另筛查 3 个 HK/新加坡 WebSearch 旁支，防止把供应商/工具异常误归到 AG Relay。
- 本地 Codex 的 `sessions` 与 `archived_sessions` 共 **72 个 rollout 文件**完成结构化扫描：30 个活动存档、42 个归档；没有 JSON 解析坏行。其工作目录均不是 AG Relay 或旧 `relay-retry-proxy`；涉及网关的讨论主要来自另一个部署/迁移项目。
- 主要依据用户正文、助手结论、相关回报，再用仓库文档、实际代码和 Git 历史核对。分叉相同部分合并；阶段性结论被新证据纠正的，保存纠正过程，不双计为两个最终结论。
- 公司旧 Codex 故障原请求不在家里，不能拿上述 72 份记录替代。公司的 21 份原日志本轮没有直接取得，只读取用户提供的完整交接。

**读取边界：**桌面对话工具返回压缩格式，很多调用只保留名称，不能称为逐字读了每一份工具输出或截图。已删除、未定位的其他客户端日志不在覆盖范围；Claude 原始持久化目录的额外访问未成功，本轮以桌面会话接口为主。

## 2. 最重要的用户要求

- 不要只告诉用户“是上游的问题”，要优先找到能保留旧对话继续的方法。
- 网关偶尔漏错误但仍可用，不能为了扩大拦截范围，破坏正常可用流程。
- 保住正文、工具调用/结果、推理连续性；能少改一个字段就不要多删一组历史。
- UA、originator、会话/线程等原生身份必须保留，临时真实测试也不能随意换成通用客户端。
- 需要追踪实际接入链路，不能只看默认供应商、模型显示名或本机端口。
- 发布与安装分开；用户多次说明自行更新本机网关。VPS 更新另行协调，不能覆盖正在更新的两站配置。
- 解释以实际现象、影响和明确建议为先。测试数可以作为证据，不能代替“原问题是否真的改善”。

## 3. 早期产品、界面与维护决定

H01～H07 七个早期会话均已分页读至开头，共 6514 条记录、19 页；长输出也已顺序读完。提炼后的决定如下：

| 主题 | 用户选择与后来结果 | 接手时保留什么 |
| --- | --- | --- |
| 产品主线 | 高峰 Astra limit/空回时少中断、少手动输入“继续”；不是把面板塞满功能 | “永不报错”是宣传目标，不是无限预算或成功保证 |
| 面板 | 复用定稿 React 工作空间，三页接真状态、真命令，删演示场景/假计时器 | 不把浏览器假数据预览当成原生成品验收 |
| 中文诊断 | 由壳侧有限字典解释结构化事件，不调用模型全量翻译原日志 | 不增加转发热路径开销，未知事件诚实回退 |
| 外部实例 | 否决设计稿“外部实例只能看不能控制”，保留停止/重启 | 要核实归属、醒目标记与二次确认，不是任意控制陌生进程 |
| 核心归属 | 规格 19 后由本仓自主维护，保留 Node/Tauri 分工 | 不再整体覆盖外部脚本，也不要求重写成单进程 |
| 连接设置 | 单上游、密钥由客户端提供；保存不立即重启 | 不扩成账号池或托管密钥系统，用户显式应用后安全切换 |
| 窗口与更新 | 关窗提供取消/留托盘/彻底退出；更新有真实阶段与下载进度 | 托盘不可用要明确，退出失败保留窗口；100%下载不等于验签或安装完成 |
| 安装包体积 | UI、字体、自带 Node 保留；大体积第三方源码改同版附件，许可原文仍随包 | 不为瘦身删除许可，也不保证覆盖升级能自动清掉旧残留 |
| 发布方式 | 试过云端签名，最后按用户选择回到本机签名、保留瘦身 | 沿用原生产密钥与现有入口；旧云端方案不是当前要恢复的任务 |
| 请求进展 | 10-14 提过等待原因、请求编号、诊断关联，后来已有契约实现 | 不重新当成整项空白功能，不顺手加 token/tok/s 采集 |

值得保留的两次纠正：

- 早期曾覆盖已发布的 v0.1.0 tag/产物，用户纠正“新版本应新建”。后来发布 v0.2.0；不能把原 v0.1.0 二进制说成已恢复。现行规则是公开 tag/Release 不覆盖，发错发新版本。
- 安装器曾尝试自动删旧许可残留，复核发现目录链接竞态后撤回；“新包变小”不等于“所有旧安装目录立即变小”。

README 选择“视觉有品牌、正文直接讲痛点”；宣传图必须区分机制示意与真实运行截图。托盘黑白 AG、桌面/侧栏可保留吉祥物的细节由公司交接补充，不等于全产品去掉吉祥物。

10-14 当时仅建议的共享冷却/`Retry-After`、背压、正文/并发边界等，不能因被说过就当现成需求；取消与分类是否后来完成，应看下一节。现行依据：[ADR 目录](../adr/)、[请求进展 UI](../request-progress-ui.md)、[发布手册](../release-runbook.md)。

## 4. 中期历史恢复、取消、等待和文档流程

H08～H14 七个会话均已完整分页读取，共 3266 条记录；H11 的 211 条全部是 H10 的共有前缀，没有新增实质结论，去重后为 3055 条。

- **激进删除策略未成为最终选择。** 用户比较过朋友的全删除方案，最终要的是正常请求尽量不动、明确错误后再有限降级，不要默认 `always` 常驻剥离。能配置不等于建议默认打开。
- **“提示修好了”不等于原始退出问题修好了。** 早期保留错误原因后仍只等 10 秒；长请求在途时退出撤销又恢复接单，用户仍出不去。后来才改成暂停新请求、等待在途归零、显示数量和时长、最长十分钟且可取消；取消/超时/租约失联恢复接单。“停止/安全重启”的旧入口没有一并改成十分钟，不能混用。
- **错误分类要跨载体一致。** 隔离探针曾证明，只把错误请求编号中的 `502` 改成 `512`，就从直接返回错误变为进入修复。统一分类后 HTTP、200 JSON、交付前 SSE 都从明确错误证据判断；编号、URL 或无关字段不能改变原因分类。
- **三次上限的适用范围曾出错。** 预清理/已登记会话不等于本次真的做了有损降级；纯限流应继续按常规预算走。v0.3.13 修正此范围，中文“无可用渠道”另按部署类重试。
- **慢请求与时间预算只是取舍，不是充分证明的最优参数。** 家里高峰调查的真实 A/B/C、完整长短请求对照当时未完成；不能把建议维持或调整某个数字写成已验证最优。后来 v0.3.14 的 220/500 秒选择由公司资料补齐。
- **文档与验证要收敛。** 用户不希望维护文档越来越大、同一事实重复读、提交发布前重复跑全部测试。最终入口改成按影响范围选择最小有效回归，长任务有截止、复用有效结果，不加通用检查工程。

证据口径更正：v0.3.10 当时只是草稿，不能列为已公开版本；后续内容由正式版本带出。v0.3.13 一次报告把五项跳过称作“需要真实通道”，README 已更正：缺的是旧核心基线，它们是本地新旧差分，不需要付费模型服务。测试跳过仍是当时缺口，不写成全部通过。

另一个标题误导是 H13“项目文档体积膨胀”：实际主要占用来自编译缓存，不是 Markdown 文档。曾获授权清掉独立测试 target、保留常用缓存，并加 `target-*` 忽略规则；当前那份 `.gitignore` 未提交改动有历史来源，不是本轮擅自新增，也不能看见它就顺手提交。更新器临时安装包清理当时只提出选项，没有执行授权。

后续具体取舍、用户停止追查的项目与公司修正，统一保存在[合并交接四类清单](combined-handoff-2026-11-01.md#七按四类保存现状)。依据：[重试边界](../retry-boundaries.md)、[核心维护说明](../gateway-core-maintenance.md)和[发布记录目录](../releases/)。

## 5. v0.3.15 → v0.3.16：搜索刚开始就漏限流

### 5.1 用户线索与一次必须保留的改判

用户反馈：0.3.15 已修过漏拦截，为什么 Codex 又迅速重连到 3/5；并提出“网页搜索后似乎更容易发生”。

最初排查只确认：请求经 CC Switch 的指定模型通道到远端，没有走家里本机网关。助手过早归结为“没经过网关”。用户随后说明 VPS 也部署了同源策略，继续核查才确认：**绕过本机不等于绕过所有网关。**

完整链路为 Codex → CC Switch → 远端入口/new-api → VPS 同源核心 → 模型上游。服务器确实已运行 v0.3.15 服务器版，流式判断与本地相同；账户隔离和部署失败计数是服务器独立定制。

### 5.2 实际缺口

旧规则把 `web_search_call` 的“开始”当成可交付内容，约两秒后出现限流时，流已发给客户端，只能透传。第一组第二、第三次重连之间没有新的正文或思考，构成较强的定位证据。

本地版与 VPS 核心副本在假上游中表现一致：

- 空思考占位后限流可以内部恢复，说明 v0.3.15 修复有效。
- 只有搜索开始后限流仍会穿透。
- 只有加密思考、无可见摘要时，也会进入交付边界；这次没有同时改动它。

**证明的是搜索开始过早交付，不是搜索导致上游限额耗尽。** 有些截图失败前已经有真实搜索结果和思考，不能承诺这一修复覆盖所有断流。

### 5.3 最终处理与验证

只针对严格 Codex Responses 的未完成搜索继续缓冲；搜索完成、真实内容或客户端工具出现时立即交付，不等整段回答结束。成功事件原字节保留，已交付不重放。

独立检查曾发现三项回归风险，随后修正：

- 搜索失败的 `.done` 不能当成成功结果。
- `response.incomplete` 的明确原因不能被吞掉再误报为空回/限流。
- 缓冲搜索不能把健康慢搜索的等待缩短成首内容超时；重复进度也不能无限续期。

最终记录：70 项流式/相邻回归与 8 项策略检查通过，包括 Claude/ZCode 新旧对照。新增真实模型请求为 0，未据此声称长期现网验收。

结果进入 v0.3.16：修复 `f452838`，发布快照 `4e902c8`。用户先批准 GitHub 发布、自行更新本机；待两站升级完成后另行批准 VPS 切换。会话记录显示只替换网关、约 11 秒完成切换与检查，两站与其他组件不动。

来源：H15/H16；[现行边界](../retry-boundaries.md#codex-search-commit)、[v0.3.16 说明](../releases/v0.3.16.md)。

## 6. v0.3.17：绑定失效后尽量保住旧历史

### 6.1 用户真正的问题

面对 `session_binding_invalidated` / `30013`，用户要知道能否剥离最少信息后继续旧对话，而不是反复听“这是上游问题”或被建议空白重开。

### 6.2 方案是怎样被证据修正的

1. 先验证原生持久化分叉：确实生成新身份、保留加载后的历史；但这只证明本地机制。
2. 用户实际分叉仍失败，说明单纯换会话编号不足。早期“分叉就能解决”不能保留为最终建议。
3. 早期真实实验用去推理+编号的组合能越过 409，但测试客户端先发的是历史整理请求，而且输出预算曾过小；不能算完整普通续聊成功。
4. 校正为真正续聊后，发现**只去编号就可以成功，推理本身可以保留**。
5. 两次去 Codex 身份的通用 UA 对照返回 401，用户明确纠正。此后禁用该入口，加入发出前及请求头组装后的身份一致性检查。
6. 最终用原生 Codex CLI、`xhigh`、相同身份生成请求，只比较剩余 24 个推理编号和 3 个搜索编号。保留编号返回历史类 400，移除后得到正文与完成事件。

全程真实客户端 HTTP 请求共 18 次，其中两次无效身份对照已排除。旧推理密文、6 段可读摘要、消息、工具参数/结果与搜索内容保留；返回工具没有执行。

**证据上限：**最终没有稳定复现原 409；支持这份旧历史的恢复方向，不证明全部未来 `30013` 都能解决，更不证明原业务已做完。

### 6.3 发布实现边界

明确错误后才尝试当次只去顶层 item id；不改 UA、会话身份或推理，不新增正常首发清理，不写入有损兼容缓存。不完整工具历史、服务端引用、纯引用推理/空消息等不盲改；同请求再报绑定/历史错误时停止升级，不继续删推理。

最终 37 项新恢复检查、12 项相邻/客户端差分、17 项诊断契约通过。修复构建提交 `baf382a`，发布快照 `59793d6`，v0.3.17 已发布。本机用户自行更新；另一个部署会话完成 VPS v0.3.17，记录本机与 Linux 隔离检查各 225 项通过，约 13.4 秒切换与检查，保留服务器定制与两站配置。

来源：H17、H15；[研究原件](session-binding-recovery-2026-10-31.md)、[v0.3.17 构建记录](../releases/v0.3.17-build.md)。研究原件仍是实现前阶段记录，不能据“尚未实施”否认后来发布。

## 7. 11 月 1 日：错误拦住了，却没有恢复

用户实际使用 VPS 的 Sol 时发现：旧对话一直卡，新对话却能成功。

家里只读调查得到：

- 一条旧请求 94 次尝试全部报 `rate_limit_exceeded`，最终失败，没有正文、思考或工具输出。
- 旧请求历史 257/259 条，含 83 条推理；新对话首轮约 5 条，后续逐渐增长。
- 新对话成功与旧对话失败在同一时间窗口；不能解释成模型整体不可用。
- 旧请求首发已经去掉全部可见条目编号，推理保留，没有看到兼容缓存误删推理的证据。
- v0.3.17 的绑定恢复没有触发；编号也已清完，不能靠再次去编号带来不同结果。

**家里当时合理结论：**旧核心确实把同类失败持续当作暂时故障重复发送，形成无进展等待；但不能确定最初拒绝是历史长度、绑定、转换、缓存条件或上游其他机制造成的。

用户授权多次真实对照，随后明确故障在公司 Codex，家里没有这份业务历史。因缺原请求，停止查错环境，**这一轮真实模型调用为 0**。这与上一节绑定恢复的 18 次不是同一实验，不应合并计数。

**公司后续更新：**v0.3.18 已实现有限缓存键恢复，并有重建 Claude Responses 的受控成功实验；原公司 Codex 严格 A/B 仍未完成。完整更正见[合并交接第六节](combined-handoff-2026-11-01.md#六两边证据对照哪些结论更新了)。不再把“换键尚未实现”作为当前待办。

来源：H15，用户提供的公司交接第 5.6 节及最新 v0.3.18 边界。

## 8. 其他工作教训

- **模型别名不是实际模型。** H18 查到一次普通子代理被主代理显式指定 `sonnet`，客户端解析为对应 Sonnet 别名，响应标识为 `deepseek-v4.1-flash`。用户期待继承主模型；不能按别名假定后端能力，也不能没有证据把其他测试失败归咎于该模型。
- **备份、缓存、本地与 VPS 要分开。** H15 的空间盘点一度扩到相邻项目，被用户要求收回 AG Relay 自己环境。本机构建缓存有复用价值；VPS 磁盘占用不占本机空间，不自动清理恢复点。
- **网站升级要协调，而不是覆盖。** VPS 网关与两站共享部署文件时，先等另一个任务完成，再对照当前镜像/配置做新备份，只改网关必要字段。旧文档的账号停用状态可能已变，不能照旧记录改回去。
- **HK/新加坡搜索异常另列。** 短测有 HTML 导致的 422 格式转换错误，也有 WebSearch 返回“不能实时搜索”的文字；另一路文档抓取曾因地区跳转报错，切换后文档可读而搜索仍异常。没有确认 AG Relay 参与，不能据此宣布搜索缓冲修复回归。HK 长旁支已完整读取本次导出的 120/127 条消息（937 行），最早 7 条未纳入；它只作为排除混淆的旁证，不作为网关根因材料。

## 11. 接手时别重新踩的坑

不要从旧结论单独复制出一个新方案：

- “只能重开”“分叉就能好”“必须删推理”“肯定是 Codex 专属”“没有走本机所以网关没问题”，都被后续证据收窄或推翻。
- “原样重试会不断换通道”“某次新键成功证明固定账户耗尽”，都不能当上游内部机制的直接证据。
- “某轮本地测试通过”“源码已修”“版本已发布”“用户已安装”“业务已恢复”，是五件不同的事。
- “公司已经做完 v0.3.18”应先同步和核对，再决定剩余工作。本轮已完成源码快进，不重复实现公司修复。
