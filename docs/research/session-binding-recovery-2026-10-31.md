# 会话绑定失效：恢复方案验证记录

日期：2026-10-31。基点：`4e902c83b2e29aa46bf51677d9151129adc4caa3`。

**阶段结论：** 更小、更保守的候选是明确错误后只去掉历史资源编号，不删除推理，也不更换客户端身份。原生 Codex CLI 的最终对照已验证旧历史可继续处理；原 409 后来变为其他历史错误，尚不能宣布所有 `30013` 情形均已解决。

全程共发送 18 次真实客户端 HTTP 请求（早期 6 次、后续 12 次），不包含仅在本地假上游进行的捕获与断言检查。没有客户端自动重试；其中 2 次改身份的对照无效，已明确排除。

## 用户要求与边界

- 目标是保留旧对话续聊，不把空白重开作为默认解决办法。
- 只有明确发生 `session_binding_invalidated`／截图中的 `30013` 类错误后，才尝试修复；正常请求不新增清理。
- **客户端身份不能改动**：原生客户端生成的 User-Agent、originator、会话／线程／窗口等身份头必须原样转发；`client_metadata`、`prompt_cache_key` 和模型身份也不改写。
- 不执行模型返回的工具，不修改原对话或现用连接配置，不安装或重启网关。

## 已确认的现场事实

本机保留的诊断中，有 18 条请求收到 HTTP 409。原对话和分叉对话使用不同会话编号，分叉后仍然失败。

对照现用网关的诊断记录，报错请求在普通首发清理后仍保留 **24 个 reasoning.id 和 3 个 web_search_call.id**。普通消息、工具条目的编号已被清理；推理内容本身没有被删除。

这与当前 `stripCodexItemIds` 的规则一致：包含网页搜索时保留推理编号和搜索编号，以免破坏它们之间的依赖。新的错误尚未被接入专门恢复入口。

## 删除范围与上下文完整性

优先候选是**只移除完整内联历史条目的顶层 `id`**，而不是删除整个 `reasoning`。

| 数据 | 只去编号的候选 |
| --- | --- |
| 聊天正文与消息顺序 | 保留 |
| 工具名称、参数、执行结果 | 保留 |
| 工具调用和结果配对的 `call_id` | 保留 |
| 搜索条目、action、status 及扩展内容 | 保留 |
| 24 条推理的加密内容 | 保留 |
| 其中 6 条推理的可读摘要 | 保留 |
| 上述条目的顶层 `id` | 移除，不递归删除内容内部的 id |
| 客户端身份头和正文身份元数据 | 原样保留 |

结构断言验证了：除指定的顶层 `id` 外，保留条目的其他值逐项相同。去编号会改变上游资源引用关系，不能称为所有协议上的通用无损变换；但它不需要直接丢弃旧推理及摘要。

**整条删除 reasoning 是另一种、更有损的处理。** 本样本有 6 条可读摘要，整条删除会连这些摘要一起从后续输入拿掉。它不是当前优先候选，也不能在只去编号失败后未经单独决策就自动升级执行。

## 真实对照及证据范围

### 早期历史整理请求

早期隔离客户端没有加载现用模型目录，兼容性定义变化使它先发起历史整理请求，而非最新的续聊指令。原编号、旧历史及重置身份的旧历史都曾返回 409；删除旧推理与编号的组合可以进入生成，并在提高测试输出预算后正常结束。

这些结果**不计为普通续聊成功**，也不能用于证明必须删除整条推理。

### 真正的续聊请求

随后加载了与现用 Codex 相同的模型目录，断言最新用户消息确实是续聊校验指令，而不是历史压缩指令。

- 原历史请求：返回历史类 400；末尾原样复测返回 403，因此不能把这组称为“稳定复现原 409”。
- 只去顶层编号、保留全部推理：正常完成并返回校验词。
- 相同请求复测：正常完成并返回校验词。
- 加入上一次真实返回后继续下一轮：正常完成并通过连续上下文校验。
- 另一次相同清理复测：通过。
- 使用用户配置的 `xhigh` 强度单独验证：通过。

这些试验支持“只去编号就能让这段旧历史继续处理”的方向；尚不能证明所有未来的同类错误都能如此恢复。

### 无效的跨客户端对照

两次“去 Codex 标识”的试验改用了通用 User-Agent，并移除了身份字段，均被上游以 401 拒绝。用户指出上游要求正规工具身份，这个试验设计破坏了前提。

**这两次不作为客户端适用范围证据，不再重试或通过其他伪装绕过。** 旧的改身份测试入口已禁止再次进行真实调用。

### 原生身份保持的现网形状对照

最后一组改为用本机原生 `codex exec resume` 生成请求，不手写 User-Agent 或客户端身份。

发送前、实际请求头组装后各检查一次：原生身份头、模型、`client_metadata`、`prompt_cache_key` 必须与捕获值一致。只有目的地址、Content-Length 等正常传输字段由 HTTP 客户端重新生成；鉴权始终使用同一份现有提供商凭据。

9 个假数据变更用例证明：删改身份字段会在发送前被拦下；只去历史条目 id 可以通过。

原生 CLI、`xhigh`、相同会话身份下的最终对照：

| 请求 | 结果 |
| --- | --- |
| 按现网首发规则处理，保留 24 个推理编号和 3 个搜索编号 | 历史类 HTTP 400 |
| 仅再去掉剩余 27 个编号，其他内容与身份字段保持相同 | HTTP 200、`response.completed`、返回预期校验词 |

第二条请求没有删除任何 reasoning、加密内容、可读摘要、工具结果或搜索内容。发送前与请求头组装后的身份一致性检查均通过。

**重要限制：最后一组也未再次复现原来的 409，而是返回历史类 400。** 因此已经证明这段旧历史可以在完整保留客户端身份和推理内容的条件下继续处理，但不能声称原 30013 的所有触发情形都已验证解决。当前产品还未接入该候选修复。

## Claude 范围

检查时 CC Switch 中选中的 Claude 方案为 Anthropic Messages 接口，不是本次 Codex 的 Responses 路径。原生 Messages 不应套用 Responses 的 `input[*].id` 清理规则。

目前没有有效的真实 Claude 对照证明它会触发或不会触发同一错误。不能宣称这是 Codex 软件天生独有的错误；同样不能因猜测“通用”就把删除策略扩展给 Claude。若以后需要比较，应使用真正的 Claude 客户端和完整身份头。

## 实现建议，尚未实施

1. 优先考虑明确错误后的当次请求、有限次数“只去编号”恢复；不新增正常首发清理。
2. 完整内联历史、支持的条目类型、工具配对都必须通过检查；遇到服务端历史引用、未知条目或不完整历史则保留原文并拒绝改写。
3. 已向客户端交付内容或工具后，不重放整个请求。
4. 不改客户端身份，不默认更换会话编号，不自动升级为删除整条推理。
5. **不能直接复用现有的整组推理降级缓存标记。** 当前 `knownCompatibility` 命中后会执行 `dropReasoning: true`；若把“只去编号”的会话登记进去，下次首发会意外删除推理。新增恢复应先限定在当次明确错误内，或另行设计分级记忆，不能混用。
6. 初始适用范围只覆盖已经验证的请求形状；Claude Messages 保持原行为。
